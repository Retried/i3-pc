# W3: portable Windows measurements

The existing bench.sh entry point now delegates to tools/benchmark.py. It reuses
the emulator's SOTC_SCRIPT actions and bench_frametimes.txt capture. Existing
perfsample.ps1 and symprof.py have been extended rather than adding another
capture mechanism inside the renderer. Runtime C++ sources are unchanged.

## Run and reproduce

Use 64-bit Windows on an AMD CPU with an NVIDIA Vulkan GPU, Python 3.11 or newer,
Windows PowerShell and vulkaninfo. Build with tools/build-windows.ps1 first;
the executable must match its adjacent build-info.json. The default game path
comes from dist/game_path.txt, and the default seed is dist/user. APP_VER 01.07
is required. --game and --user-seed override these inputs.

```powershell
python tools/benchmark.py run --executable runtime/Build/w2-x64-Clang-RelWithDebInfo/shadps4.exe --matrix docs/benchmark-control.json --out runtime/Build/my-control-series --repeats 3
python tools/benchmark.py report runtime/Build/my-control-series
```

From Git Bash, bench.sh accepts the same subcommands and arguments;
PYTHON3_EXECUTABLE can select Python. Paths are resolved from arguments/the
checkout. Existing output directories are rejected. A HOLD file or another
known emulator/build process prevents a new run; no other process is killed.
Timeout termination targets only the child launched by this runner.

cpuframe.sh now reads a completed suite and reports approximate render-thread
CPU/frame from the existing three-second counters. Legacy clip-generation tools
are outside this runner; their sampler arguments/CSV reader remain compatible,
but their hardcoded routes/paths are not a supported W3 capture workflow.

Each series snapshots the executable, optional PDB, build metadata, seed and
harness files. Each run gets a new directory and private copy of saves/settings;
the original seed is not a write destination. Absolute home/module/font overrides
are cleared to retain that isolation. The immutable binary snapshot is linked
into each run directory. Logs, scripts, source state, file hashes and hardware
metadata are retained. Run directories contain private copied user data and stay
ignored by Git; published reports contain measurements/provenance, not those files.

## Conditions and cache

The recorded configuration requests a 1920x1080 window/internal size, Immediate
presentation and a 144 Hz frame clock. Captured images/logs must still be checked
for actual scene and output dimensions. Existing graphics effect settings are
copied and hashed, not silently upgraded. A hidden SDL window and dummy audio
avoid desktop capture/input and audio output; this defines the measured mode.

Cold means a new empty emulator shader/pipeline cache. Warm runs each receive
the same immutable cache generated by one full primer for that scene. The
NVIDIA driver cache is not cleared or controlled. These must not be described
as fully cold driver-cache measurements. The primer is excluded from reported
repeats. --caches selects separate cold/warm series.

For same-binary/same-GPU-driver follow-ups, --warm-seed can reuse a prior suite's
warm-seed directory. It is copied into the new suite, checked against the prior
binary/GPU metadata, and hashed for every run. It requires a single-scene matrix.

JSON scene matrices specify warm-up time, measurement duration, boot actions and
route actions relative to the measurement start. Variant environment variables
are explicit; experimental I3_/SOTC_ variables inherited by the caller are
removed before starting the defined run. A/B order alternates between repeats.
Vulkan validation settings are disabled for timing; validation runs remain
separate. An explicitly forced Khronos layer prevents timing capture.

## Raw data, metrics and interpretation

Each result retains the original frame intervals. The first captured interval
straddles bench=on, so exactly one boundary interval is excluded. No other
outliers are removed. Nonfinite/nonpositive intervals, fewer than 100 frames,
failed exit, critical/device-loss log matches, wrong game/GPU or duration beyond
the documented tolerance invalidate a run. Raw invalid runs remain as evidence.

- Average FPS = 1000 / mean(interval milliseconds).
- 1% low = 1000 / mean(the slowest ceil(N*0.01) intervals).
- Percentiles use linear interpolation at ordered position (N-1)*p.
- Report median, p95, p99, worst frame, and the minimum/maximum/standard deviation
  across independent repeats. Cold and warm groups are never combined.
- Missing telemetry is null/empty, not zero. CPU load is PID scoped and normalized
  to logical processors; busiest-thread load is a per-core percentage. NVIDIA
  utilization, VRAM, power and temperature describe the whole selected card.
  GPU frame timing is unavailable in this capture mode.

summary.json, summary.csv and summary.md are regenerated from valid result files.
For off/on groups, the report compares the mean delta with the observed range
among repeats, requires at least three per variant for that check, and labels
the comparison as descriptive. This is not a fixed regression threshold,
statistical significance test or automatic correctness acceptance. Representative
scenes, visuals, stability and the second PC remain acceptance requirements.

To collate two PCs or suites without inventing missing cases:

```powershell
python tools/benchmark.py compare runtime/Build/pc-a-series E:/Imported/pc-b-series --out runtime/Build/two-pc-comparison.json
```

Machine IDs, hardware/build metadata, matching case rows and null missing cases
are retained. Matching scene/settings/save conditions must be verified before
interpreting hardware differences. Two local suites do not count as two PCs.

## Profiling for W4

--profile enables the existing render-thread stack sampler only for a separate
profiling run. Its frame timings are excluded from benchmark summaries. The
runner snapshots valid histograms near the measurement boundaries and records
the process image load base. The sampler resets its counters every ten seconds;
each file represents one completed interval, and the two files must not be
subtracted. symprof.py accounts for ASLR without rewriting the executable:

```powershell
python tools/symprof.py --profile <run>/profile-after.txt --exe <suite>/binary/shadps4.exe --load-base <recorded-image-load-base> --symbolizer <llvm-symbolizer.exe> --out <run>/symbols.json
```

The sampler scans three executable return-address candidates rather than
unwinding the stack; results are approximate. Its snapshots update every ten
seconds; profile-after is the latest completed interval near the window end,
not the entire thirty-second measurement. Nearest
executable frame is not necessarily the actual leaf when the thread is in a
driver or system wait. LLVM's relative-address handling is described in the
[llvm-symbolizer manual](https://llvm.org/docs/CommandGuide/llvm-symbolizer.html).
Keep sampler overhead out of performance comparisons. Existing renderer time
counters overlap/nest and must not be summed into an exclusive CPU breakdown.

## Tool verification

Python syntax/ASCII and PowerShell parsing were checked; all changed Bash entry
points passed syntax checks. An independent known frame distribution verified
average FPS, slowest-one-percent averaging and percentile interpolation. Actual
raw frame hashes and metrics were recomputed from the six W3 captures. The CPU
report was exercised against captured windows and correctly marks older runs
without a captured counter window unavailable. Symbolization used the actual
profile and matching PDB, with zero unknown nearest frames. No repository test
files or renderer test targets were added.
